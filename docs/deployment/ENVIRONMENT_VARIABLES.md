# Production environment variables

Every setting a staging or production server needs, how to create it safely, and how to check it before anything starts. The complete reference for all optional tuning variables stays in [../configuration.md](../configuration.md).

**No real secret belongs in this repository.** The real values live in one file, `.env.production`, that exists only on the server (and a copy of the irreplaceable ones in your password manager). `.gitignore` and `.dockerignore` exclude it, CI fails if an environment file is ever committed, and the checking script never prints a value.

## The three files

| File | Where it lives | Contains secrets | Purpose |
|---|---|---|---|
| `.env.production.example` | In the repository | No | Template to copy |
| `.env.production` | **Only on the server**, mode `600` | **Yes** | The real configuration of that one environment |
| `release.env` | Only on the server | No | The two image names of the running release, written by `scripts/deploy/deploy.sh` |

Development uses a different file (`.env`, from `.env.example`) and a different Compose file, so development and production settings cannot mix. Staging and production are two servers, each with its own `.env.production` and **its own secrets**.

## Step by step

Run these on the server, in the deployment directory (for example `/srv/autowok`).

```sh
cp .env.production.example .env.production
chmod 600 .env.production                      # only your user can read it
sh scripts/deploy/generate-secrets.sh          # prints 8 fresh secrets
nano .env.production                           # paste them in, then fill in the address section
sh scripts/deploy/preflight.sh                 # checks everything, prints only setting NAMES
```

`generate-secrets.sh` needs only `openssl`, writes nothing to disk and contacts nothing. Its output is secret: do not paste it into chat, email, a ticket or git.

`preflight.sh` answers `READY` or lists each problem as `FAIL  <SETTING NAME> <what is wrong>`. It checks the file, then the Compose file, then loads the settings inside the backend image using the application's own start-up rules, without starting any service.

## Variables you must set

### Public address

| Variable | Example | Rule |
|---|---|---|
| `APP_ENV` | `production` | `production` on staging too, so staging runs the same safety checks. |
| `SITE_ADDRESS` | `app.your-domain.com` | The host name only. The proxy gets the HTTPS certificate for it. |
| `PUBLIC_ORIGIN` | `https://app.your-domain.com` | Exactly `https://` + `SITE_ADDRESS`. No path, no trailing slash. Becomes the CORS allowed origin, the address compiled into the web app, and the base of media links Meta downloads. |
| `ALLOWED_HOSTS` | `app.your-domain.com` | Host names the API will answer for (trusted hosts). Must contain `SITE_ADDRESS`. |
| `ACME_EMAIL` | `you@your-domain.com` | Receives certificate expiry warnings from Let's Encrypt. |

The Compose file derives the rest from these, so they cannot disagree: `CORS_ORIGINS` = `PUBLIC_ORIGIN`, `PUBLIC_MEDIA_BASE_URL` = `PUBLIC_ORIGIN`, `SESSION_COOKIE_SECURE=true`, `SESSION_COOKIE_SAMESITE=lax`, `APP_DEBUG=false`, `LOG_FORMAT=json`.

### Secrets (all generated by `generate-secrets.sh`)

| Variable | Protects | If it is lost | If it leaks |
|---|---|---|---|
| `POSTGRES_PASSWORD` | The database | Reset it in PostgreSQL | Rotate; the database is not reachable from the internet, so exposure also needs server access |
| `REDIS_PASSWORD` | Redis | Set a new one and restart | Rotate |
| `AI_ENCRYPTION_KEY` | Saved workspace AI (Groq) keys, encrypted in the database | **Every workspace must enter its AI key again** | Rotate with the rotation script |
| `TOKEN_ENCRYPTION_KEY` | Saved Facebook/Instagram tokens, encrypted in the database | **Every account must be reconnected** | Rotate with the rotation script |
| `MEDIA_URL_SIGNING_SECRET` | The expiring links Meta uses to download media | Links in flight stop working; jobs retry | Rotate when nothing is publishing |
| `METRICS_TOKEN` | `/metrics` and `/api/v1/health/details` | Set a new one | Rotate |
| `META_OAUTH_STATE_SECRET` | The "connect Facebook" flow against forgery | Connections in progress start again | Rotate |
| `BACKUP_PASSPHRASE` | Backup encryption | **Existing backups can never be opened** | Rotate for future backups |

**Save these four in a password manager on the day you create them:** `AI_ENCRYPTION_KEY`, `TOKEN_ENCRYPTION_KEY`, `MEDIA_URL_SIGNING_SECRET`, `BACKUP_PASSPHRASE`. The first two are deliberately not stored in the database, and the passphrase must not be stored with the backups.

Rules the checks enforce: database and Redis passwords are 32+ letters and digits (they sit inside connection addresses, where symbols would break); the two encryption keys are valid and different from each other; no secret is reused for two settings. Rotation procedures: [../security/security-assessment.md](../security/security-assessment.md#secret-rotation).

### Meta (Facebook and Instagram)

| Variable | Where the value comes from |
|---|---|
| `META_APP_ID` | Meta for Developers → your app → App settings → Basic |
| `META_APP_SECRET` | Same page ("App secret"). Backend only. |
| `META_GRAPH_API_VERSION` | Default `v26.0`. Before launch, confirm in the Meta dashboard that this version is still supported. |
| `META_REDIRECT_URI` | Exactly `PUBLIC_ORIGIN` + `/api/v1/oauth/meta/callback`. The same text, character for character, must be in the Meta app under Facebook Login → Settings → Valid OAuth Redirect URIs. |
| `META_OAUTH_STATE_SECRET` | From `generate-secrets.sh` |

Leave `META_APP_ID` empty to run without Facebook/Instagram features (the app starts; connecting an account reports that Meta is not configured). Use a **separate Meta app for staging**, in Development mode. Full setup and review requirements: [STAGING_DEPLOYMENT.md](STAGING_DEPLOYMENT.md#meta-app-for-staging) and [PRODUCTION_DEPLOYMENT.md](PRODUCTION_DEPLOYMENT.md#meta-app-review-and-business-verification).

### Groq (the primary and only AI provider)

| Variable | Notes |
|---|---|
| `GROQ_API_KEY` | Optional platform key from console.groq.com. **Backend only**: it is read by the API and worker, encrypted in transit to Groq, never sent to the browser and never logged. Leave empty to require each workspace to save its own key in Settings → AI. |
| `GROQ_DEFAULT_MODEL` | A model id from the live list shown in Settings → AI. |
| `GROQ_ENABLED` | `true`. |
| `AGENT_GROQ_MODEL` | Optional model for multi-agent workflows. |

A platform key is shared by every workspace that has not saved its own, so its rate limits and any bill are yours. The per-user limits (`RATE_LIMIT_AI_*`) cap how fast it can be used. Autowok accepts only the official Groq address (`api.groq.com`) and contains no fallback to another paid AI provider: if Groq refuses a request, the user sees the error.

### Email (workspace invitations)

| Variable | Meaning |
|---|---|
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` | Mail server address, port and connection type (`starttls` for port 587, `ssl` for 465, `none` only for a local test server). Empty `SMTP_HOST` switches email off. |
| `SMTP_USERNAME`, `SMTP_PASSWORD` | Mail server sign-in. **Secret.** For Gmail use an app password. |
| `SMTP_FROM` | Sender shown to the recipient, for example `Autowok <no-reply@example.com>`. Must be an address your mail server lets you send from. |
| `INVITATION_EXPIRY_DAYS` | How long an invitation link works (default 7). |

With email off, inviting someone still creates the invitation and shows the link once to the admin, to pass on by hand. The link's address comes from the first entry in `CORS_ORIGINS` (the public address of the web app). Tested with a simulated mail server only; delivery through a real SMTP server has not been verified.

### Research search provider

| Variable | Notes |
|---|---|
| `RESEARCH_SEARCH_PROVIDER`, `RESEARCH_SEARCH_API_KEY`, `RESEARCH_SEARCH_BASE_URL` | Optional. Set the provider to `groq` (uses a Groq API key and Groq's built-in web search; about 5,500 Groq tokens per run, sources mostly without summaries), `tavily` or `brave`, and the key to that service's API key; leave the base URL empty to use the provider's official address. With these empty, running research reports that no provider is configured. Usage is billed by the provider. `groq` was verified live once on 2026-11-17 (10 sources returned); `tavily` and `brave` are tested with simulated answers only. |

### Backups

| Variable | Notes |
|---|---|
| `BACKUP_PASSPHRASE` | Required; the backup refuses to run unencrypted. |
| `BACKUP_RETENTION_DAYS` | `14`: local backup sets older than this are deleted. |
| `BACKUP_HOST_DIR` | Folder on the server where backup sets are written. They must also be copied off the server ([BACKUP_AND_RECOVERY.md](BACKUP_AND_RECOVERY.md)). |

### Monitoring

| Variable | Notes |
|---|---|
| `METRICS_ENABLED` | `true` |
| `METRICS_TOKEN` | From `generate-secrets.sh` |
| `SENTRY_DSN` | Optional and currently **inactive**: the `sentry-sdk` package is not in the image, so a DSN alone does nothing except log a warning. Errors always go to the structured log. |
| `RELEASE_VERSION` | Optional label (for example the commit) shown in error reports. |

## Variables you should not set

| Variable | Why |
|---|---|
| `DATABASE_URL`, `REDIS_URL` | Built by the Compose file from the passwords above. Set them only when using a managed database ([DATABASE_DEPLOYMENT.md](DATABASE_DEPLOYMENT.md#using-a-managed-postgresql-service)). |
| `CORS_ORIGINS`, `PUBLIC_MEDIA_BASE_URL`, `SESSION_COOKIE_*`, `APP_DEBUG`, `LOG_FORMAT`, `LOCAL_STORAGE_PATH` | Fixed by the Compose file to safe values. |
| `API_DOCS_ENABLED` | Leave unset: the interactive API documentation stays off in production. |
| `FORWARDED_ALLOW_IPS` | Set by the Compose file. Change only if another proxy or CDN is placed in front ([../deployment.md](../deployment.md#behind-another-proxy-or-load-balancer)). |
| Anything starting with `NEXT_PUBLIC_` | Such values are visible to every visitor. The only one is the public address, set automatically during the image build. **Never put a key or password in a `NEXT_PUBLIC_` variable.** |

## What the application refuses to start with

In production the API and the worker stop immediately, naming the setting, if: debug is on; the database password is empty or a known default; an allowed origin is not `https://`; an encryption key is missing, malformed, or the two are identical; the media signing secret is shorter than 32 characters; Meta is half-configured or its redirect is not `https://`; metrics are on without a 24+ character token; or cross-site cookies are requested. CI proves this on every change by starting the production image with no secrets and expecting it to fail.

## GitHub secrets (for the deployment workflows only)

These let GitHub Actions reach the server over SSH. They are stored in GitHub's encrypted environment secrets, never in workflow files, and **none of them is an application secret**.

| Environment | Secrets | Variable |
|---|---|---|
| `staging` | `STAGING_SSH_HOST`, `STAGING_SSH_USER`, `STAGING_SSH_KEY`, `STAGING_SSH_KNOWN_HOSTS`, `STAGING_DEPLOY_PATH` | `STAGING_PUBLIC_ORIGIN` |
| `production` | `PRODUCTION_SSH_HOST`, `PRODUCTION_SSH_USER`, `PRODUCTION_SSH_KEY`, `PRODUCTION_SSH_KNOWN_HOSTS`, `PRODUCTION_DEPLOY_PATH` | `PRODUCTION_PUBLIC_ORIGIN` |

Use a dedicated SSH key per environment (not your personal key), and give each GitHub environment "Required reviewers" so a run waits for approval before it can read them.

## Changing a value later

1. Edit `.env.production` on the server.
2. `sh scripts/deploy/preflight.sh`
3. `docker compose --env-file .env.production --env-file release.env -f docker-compose.prod.yml up -d`

Changing `SITE_ADDRESS` / `PUBLIC_ORIGIN` also requires rebuilding the web image (the address is compiled into it), and updating the Meta redirect URI. See [PRODUCTION_DEPLOYMENT.md](PRODUCTION_DEPLOYMENT.md#domain-dns-and-https).
